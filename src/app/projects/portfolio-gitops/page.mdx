  <CaseStudySection id="summary" number="1" title="Executive summary">
    This repository provisions and operates a personal portfolio cluster on Oracle Cloud Infrastructure ARM compute without manual SSH work after the initial VM click. A generated cloud-init payload installs K3s, bootstraps Infisical for secret management, and hands ongoing control to FluxCD. Flux continuously reconciles the desired state from Git, making changes auditable, reviewable, and reversible.

  <CaseStudySection id="decisions" number="4" title="Key technical decisions" className="mt-14">
    <div className="space-y-8">
      <DecisionBlock number="1" title="FluxCD over Argo CD">Flux image automation polls GHCR, selects images by policy, commits tag updates, and triggers redeploys as one closed loop. Its smaller footprint also suits a constrained single-node cluster. The tradeoff is that automated <code>fluxcdbot</code> commits and alphabetical tag ordering become part of the operating model.</DecisionBlock>
      <DecisionBlock number="2" title="K3s with Traefik disabled, then re-owned by Flux">K3s ships with Traefik, but two owners for the same controller create conflicts. Disabling the bundled install gives Flux exclusive ownership, accepting a short ingress-free interval during a clean bootstrap.</DecisionBlock>
      <DecisionBlock number="3" title="Infisical over sealed secrets or SOPS">The operator uses the cluster’s own Kubernetes identity rather than static credentials. A transient Infisical outage can delay rotation but does not interrupt already-running pods.</DecisionBlock>
      <DecisionBlock number="4" title="Gateway API and DNS-01 wildcard TLS">Gateway API is the only enabled Traefik routing provider. DNS-01 supports wildcards without requiring an HTTP challenge endpoint, allowing one certificate to cover current and future subdomains.</DecisionBlock>
    </div>
  </CaseStudySection>

  <CaseStudySection id="bootstrap" number="5" title="The bootstrap chicken-and-egg problem" className="mt-14">
    Flux needs an SSH key to connect to GitHub, but that key lives in Infisical and the Infisical operator needs a running cluster. Cloud-init resolves the cycle in two phases: first it creates K3s and the minimum Infisical setup required to fetch the Flux key; then it bootstraps Flux, which assumes full ownership. Cleanup removes bootstrap artifacts and the temporary key afterward.

    Application images follow a comparable loop: CI pushes to GHCR, Flux image automation discovers a permitted tag, commits the selected version to Git, and Flux reconciles the resulting rollout.
  </CaseStudySection>

  <CaseStudySection id="constraints" number="6" title="Reliability & constraints" className="mt-14">
    The system is deliberately candid about its limits. It runs on a single OCI node, so reboot or maintenance produces full downtime. pgvector uses K3s local-path storage with no backup mechanism; embeddings and metadata are at risk on node failure. At full load, parser and database workloads compete on a constrained CPU budget.
